# WinSetup — финальное ТЗ для Claude (UI/UX)

## Цель
Сделать из текущего WinSetup удобную, аккуратную Windows desktop-программу для первичной настройки системы после переустановки Windows. Это не «оптимизатор Windows», не магазин с рейтингами и не просто оболочка над одной кнопкой. Основной сценарий: выбрать программы → проверить/настроить параметры → просмотреть очередь → установить → увидеть достоверный итог и фактические пути.

## Референсы: какие идеи использовать

1. **UniGetUI** — понятные списки пакетов, сведения об источнике/издателе, массовый выбор, отдельные представления для доступных пакетов, установленных приложений и обновлений, экспорт/импорт.
2. **Ninite** — максимально короткий основной сценарий и отсутствие необходимости разбираться в технических деталях для обычной массовой установки.
3. **WinGet** — реальные операции и ограничения пакетного менеджера: install, list, upgrade, uninstall, export/import; параметры установщика зависят от конкретного manifest/installer.

Не копировать чужую графику, бренд, иконки или код. Использовать только принципы информационной архитектуры и UX.

## Предлагаемая структура приложения

### Основная навигация
- **Каталог** — поиск, категории, фильтры, карточки/компактный список.
- **Установленные** — обнаруженные приложения, версии, источники и реальные пути, если известны.
- **Обновления** — только когда реальная проверка WinGet/provider вернула доступные обновления.
- **Очередь** — выбранные задачи, этапы, прогресс, отмена, ошибки и итог.
- **Профили** — наборы приложений для повторной настройки ПК.

Настройки, инструменты, журнал и диагностика должны быть в отдельном разделе/меню, а не россыпью кнопок над каталогом.

### Верхняя панель каталога
Оставить только:
- заголовок и краткое описание текущего раздела;
- широкое поле поиска;
- компактный фильтр/сортировку;
- одну главную кнопку действия, если она контекстно нужна;
- кнопку меню «Дополнительно» для редких действий.

Не держать постоянно видимыми кнопки «Проверить WinGet», «Установить WinGet», «Проверить программы», «Повторить ошибки», «Журнал», «Папка программ», «Пути и папки», «Создать папки». Разнести их по контекстным меню, «Инструменты» и настройкам.

### Карточка приложения
Показывать:
- настоящий логотип, если он легально и надёжно доступен; иначе буквенный/геометрический fallback;
- название, короткое описание, категорию;
- понятный статус: Не установлено / Установлено / Доступно обновление / Установка / Ошибка / Требуется отдельный сценарий;
- checkbox или кнопку добавления в очередь;
- вторичные действия через контекстное меню.

Не показывать выдуманные рейтинги, размеры, версии или издателей. Не перегружать карточку техническим текстом. Полный путь и диагностику показывать в подробностях.

### Очередь и нижняя панель
- В обычном режиме — компактная закреплённая панель: количество выбранных, основная кнопка «Установить», ссылка/кнопка «Очередь».
- Во время выполнения — отдельный экран/панель очереди: текущая задача, этап, общий прогресс, прогресс по задачам, отмена, лог/детали.
- Итог: Успешно / Предупреждения / Ошибки / Пропущено; по каждой задаче отдельная причина.
- Не показывать «Успешно», если подтверждён только запуск WinGet. Разделять результат команды и независимое обнаружение установленного приложения.

### Установленные приложения
- Имя, версия, publisher/source (только если реально получены), фактический путь (если достоверно найден), статус.
- Действия Update / Uninstall / Repair только когда provider поддерживает их для конкретного пакета.
- Не создавать фиктивные кнопки и не показывать одинаковые действия для всех типов установщиков.

### Профили
- Создать, переименовать, сохранить, загрузить, удалить.
- Позже предусмотреть импорт/экспорт JSON, но не рисовать неработающие элементы.
- Показывать количество программ и дату последнего изменения.

### Настройки
- Корневая папка установки с явным предупреждением: поддержка зависит от installer.
- Папки/шаблоны — отдельная настройка; создание папок не означает перемещение/установку программ.
- WinGet readiness/bootstrap, журнал, очистка временных файлов — в «Инструментах».
- Объяснить, что bootstrap App Installer может требовать системные зависимости/политики и подтверждение Windows.

## Визуальное направление
- Тёмный графитовый интерфейс, спокойный красный акцент только для важных действий/выбранного состояния.
- Чёткая типографика, единая шкала отступов, аккуратные границы.
- Уменьшить количество вложенных рамок и скруглений.
- Никакого тяжёлого blur/glass, гигантских карточек и бессмысленных анимаций.
- Минимум 1120×720, корректное масштабирование при 1280×720, 1440×900 и более широких окнах.
- При узкой ширине — адаптивная сетка карточек или переключение на компактный список; не обрезать панель действий.
- Видимый keyboard focus, tab navigation, tooltips для иконок, контрастные disabled/error states.
- Стиль должен выглядеть как законченная утилита Windows, а не веб-панель.

## Обязательные состояния
- Первый запуск / WinGet не найден.
- WinGet готов.
- Каталог загружается / пустой поиск / ошибка поиска.
- Выбрано 0 / выбрано несколько.
- Программа установлена / не установлена / путь неизвестен / путь отличается от запрошенного.
- Установка в очереди / скачивание / проверка / установка / обнаружение / очистка.
- Отмена / перезагрузка требуется / ошибка / предупреждение / пропущено — отдельные статусы.
- Личный элемент каталога и его редактирование.

## Технический контракт — не ломать

Проект: C# + WPF + .NET 10, `WinSetup.csproj`.

Сохранять функциональность и совместимость:
- `AppEntry`: Name, Category, Description, WingetId, GitHubRepo, IsCustom, IsSelected, Status, InstalledPath, InstalledVersion.
- `AppCatalogStore`: `%LOCALAPPDATA%\WinSetup\Catalog\custom-apps.json`.
- `UserSettingsStore`: profiles, folders, install root.
- `InstallerService`: WinGet bootstrap, подпись App Installer, запуск процесса через `ProcessStartInfo.ArgumentList`, прогресс, отмена, лог, проверка установленных приложений и фактического пути.
- Существующие handlers: `SearchBox_TextChanged`, `Install_Click`, `CancelInstall_Click`, `Folders_Click`, `CreateFolders_Click`, `AddApp_Click`, `EditCustomApp_Click`, `DeleteCustomApp_Click`, `CheckInstalled_Click`, `RetryFailed_Click`, `CheckWinget_Click`, `InstallWinget_Click`, `ChooseInstallRoot_Click` — либо сохранить, либо обновить все ссылки согласованно.
- Существующие данные LocalAppData не удалять и не менять формат без миграции.
- Не менять package IDs, installer arguments, source selection, Authenticode checks и security behavior в рамках UI-only работы.
- Не переносить process/network/filesystem logic в code-behind ради визуального эффекта.
- Не добавлять фиктивные кнопки или mock interactions.

## Обязательный рабочий процесс Claude
1. Сначала прочитать `PROJECT_AUDIT.md`, весь проект и текущий `README.md`.
2. До редактирования выдать короткий план и список файлов.
3. Разделить UI и бизнес-логику. В рамках первого прохода — редизайн без изменения семантики сервисов.
4. После редизайна проверить все XAML names, bindings, styles, event handlers, resources, namespaces.
5. Собрать Release `win-x64` через `dotnet publish`.
6. Исправить все ошибки компиляции и XAML.
7. Запустить приложение и вручную проверить каталог, поиск, категории, add/edit/delete custom app, профили, папки, install queue, cancel, logs, WinGet readiness.
8. Если реальный Windows runtime недоступен — честно перечислить непроверенное, не заявлять успех.
9. В конце дать список изменённых файлов, результаты build/runtime тестов, известные ограничения и ZIP проекта.

## v0.8.5 installation contract — preserve this behavior
- The chosen folder is a parent/root. Each app gets a sanitized child directory named after its catalog entry.
- Pass the per-app directory to WinGet as `--location`; use exact, reviewed vendor-specific overrides for Firefox (`/InstallDirectoryPath`) and VLC (WiX MSI `APPLICATIONFOLDER`).
- Verify the detected install path against that individual child directory. A mismatch or unknown path is an error when a target was selected.
- Existing apps outside the target child directory trigger a reinstall attempt; do not silently skip them. Never automatically uninstall or move the old copy.
- Generic installers may ignore custom paths. Do not claim universal support; report the actual path and add a reviewed package-specific strategy when needed.

## v0.8.5 installation folder behavior
The selected directory is a parent/root. Each application must be installed into its own sanitized child folder named after the catalog entry. Current implementation uses per-app child paths, a Firefox `/InstallDirectoryPath` override, and a VLC WiX MSI `APPLICATIONFOLDER` override. Post-install verification must compare the actual location to that exact child folder. Preserve this behavior during UI refactoring; do not revert to one shared folder or claim generic support for installers that ignore custom paths.
